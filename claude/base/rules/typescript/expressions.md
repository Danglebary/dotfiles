# TypeScript: expressions and iteration

- **No ternaries.** Spell the branching out as explicit `if` blocks. Control flow's split-compound-conditions rule governs the boolean-gate half of this preference.
- **Avoid coalescing altogether.** No `??` or `||` defaulting — an inline fallback silently papers over the absence it handles. Make the nullish case an explicit `if` branch: assert it away, default it visibly, or handle it — same spirit as the ternary ban.
- **Prefer `switch` over repeated `if`s on one discriminant.** When several branches test the same value for equality, a `switch` names the discriminant once and presents the branch set as one checkable whole — an `if` chain restates the comparison per branch, and a value matching no branch passes the last one silently, whereas a `switch` over a union takes the `satisfies never` default arm plus `unreachable`, turning that omission into a compile error and a crash. Control flow's split-compound-conditions rule is undisturbed — it governs compound boolean conditions, not same-discriminant dispatch — and repeated `if`s remain correct where the tests are not one discriminant's equality (mixed predicates, ranges, type guards).
- **Avoid anonymous functions; prefer named functions defined outside the enclosing scope.** A hoisted named function gives stack traces and profiles a name, can't accidentally close over local state, and keeps call sites readable (`items.filter(isSettledAccount)` over an inline arrow). Inline arrows are for when a closure over local state is the point.
- **Prefer `for`/`for…of` loops over array methods.** A loop is explicit control flow: the bound, the early exit, and an inline assertion per iteration all come free, it consumes any `Iterable`, and one pass does what a chain does in several. It is also the construct that cannot be fused — a loop body is statements, so the density Statement shape forbids has nowhere to form. Where a single-step transform genuinely reads better as a method call, the rules on type-guard `.filter` and `Array.from` over `.map` govern it; a chain of two or more is the smell this targets.
- **`.filter` predicates are type guards.** Write the callback as `(x): x is Narrowed => …` so the resulting element type narrows; a filter that discards a union member while the type stays wide is the smell this targets.
- **Prefer `Iterable<T>` over `T[]` in signatures** when iteration is all the function needs — callers can pass arrays, generators, `Set`s, and `Map` views alike, and the function can't accidentally index into or mutate its input.
- **Prefer generators for producing sequences.** A `function*` that yields beats building intermediate arrays — lazy, memory-bounded, and composes with `Iterable`-typed inputs.
- **Prefer `Array.from(iterable, fn)` over `.map()`** — it accepts any `Iterable`, maps in a single pass without the intermediate array, and is the natural materialization point at the end of a generator pipeline. This rule and the generator rule choose which construct produces a sequence; Statement shape's one-operation rule bounds how many constructs share a statement, so `const pending = Array.from(batch, fetchCardFacts);` stands on its own line.
- **A regex names a token; a loop parses.** Where a command line, a header, or a line format has structure, one small pattern says what a word is and a loop walks the words, deciding per word under an explicit bound, so the grammar lives in control flow a reader can follow and the run time is linear by construction. A single large pattern that carries the grammar hides its bound inside the engine: an alternation under `*`, `+`, or `{n,}` is linear only while its alternatives can never match the same text, which no reader re-checks on the next edit, and once it stops holding the engine tries every split of the input and the pattern goes exponential. Where the alternatives are disjoint by construction and the pattern is the clearest form, say so in a comment, and a body of plain runs separated by escapes is written unrolled, `[^"\\]*(?:\\.[^"\\]*)*`, so no alternation sits under the repetition. Several small named patterns beat one large one for the reason several named statements beat a fused expression: each can be checked alone.
