# External APIs

- **External API calls follow the bounded-read contract.** Multi-item fetches carry an explicit bound or paginate, Performance's 100-record ceiling applies per request, and pagination is wrapped in a lazy sequence over the provider's paging mechanism — preferring its cursor or page-token scheme where offered, falling back to page or offset parameters — so call sites consume every paginated source the same way.
- **Documented error codes never throw.** An error code the provider's API documentation describes is a known outcome, not an exception: accept it as legitimate and handle it appropriately — Errors' don't-throw-for-known-outcomes rule extended to the provider's contract. Throwing is reserved for what the documentation does not account for: network faults, unrecognized statuses, malformed payloads.
- **Every external-API module carries an agents file.** The module integrating a provider ships an `AGENTS.md` describing the API: what it is and what the integration uses it for, the authoritative documentation sources (the same links the error-handling comments cite), auth and configuration expectations, and how the module should be used from the rest of the codebase. An agent landing in the integration reads the contract before the code — and the file is kept current as the integration changes.
- **Cite the documentation where known errors are handled.** The branch that handles a documented error code carries a comment linking the provider's API documentation for that code, where known — the reader verifies the contract the branch encodes against the source, not against model memory or folklore.
- **Doc citations are dated.** Every API-doc comment carries the date it was last verified (`// https://… — checked 2026-08-13`): a citation is a claim about when the contract was last true, not a permanent fact. When code near an aged citation is touched, re-fetch the doc, confirm the contract still holds (fix the code if it doesn't), and refresh the date.
- **Inbound webhooks always verify the sender.** Every webhook endpoint authenticates the delivery by the provider's documented mechanism — signature verification over the raw body with the timestamp checked against replay, mutual TLS, or a shared secret — before the payload is parsed or acted on. Where the provider publishes source IP ranges, a strict IP allowlist is applied in addition, never instead. A delivery that fails verification is rejected, not processed leniently.
- **Retries are bounded, explicit, and transient-only.** Retry only failures the provider's contract marks transient — network faults, timeouts, 408/429/5xx as documented — never other 4xx client errors. The attempt count, per-attempt timeout, and total deadline are explicit at the call site: a retry loop is a loop, and Control flow's put-a-limit-on-everything rule bounds all three.
- **Back off exponentially, with jitter, honoring `Retry-After`.** Delay doubles from an explicit base to an explicit cap, with jitter so synchronized callers don't stampede the provider; a documented `Retry-After` header (429/503) overrides the computed delay. The sleep is cancelable, so cancellation composes instead of leaking timers.
- **Retry only what is safe to repeat.** Idempotent requests retry freely; a non-idempotent request retries only through the provider's idempotency mechanism (idempotency keys, documented) — without one, the failure goes back to the caller as a known outcome rather than risking a duplicate side effect.
